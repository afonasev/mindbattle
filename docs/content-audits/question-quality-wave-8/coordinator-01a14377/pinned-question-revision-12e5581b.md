# Ревизия вопросов: исполнимый процесс

Решение о пересмотре процесса: пользователь, 2026-10-14, чат 01a13b21-6800-7843-9ab6-f255503aafda.
Этот документ регулирует организацию работы. Требования к достоверности, независимой проверке,
сложности и frozen scope не отменяются. Закрытие старых чатов не означает приёмку вопросов.

## Единица работы и роли

- Одна задача — 10–20 конкретных ID одной темы, один baseline SHA, один авторский результат.
  Тематический контекст и соседние карточки доступны для чтения; завершение всей темы не является
  условием передачи готовой части. 500/2000 — размер очереди, не размер исполнительного поручения.
- Один координатор ведёт очередь и интеграцию; один автор готовит конкретную часть; другой человек/агент
  независимо проверяет получившийся CURRENT. Координатор выполняет adjudication и проверку
  согласованности вердиктов, но не делает третью полную содержательную ревизию.
- Применение точного patch и сохранение выполняет координатор обычными инструментами.
  Отдельный opaque-editor или capture-чат нужен только при конкретной технической необходимости,
  а не как обязательный этап для каждой карточки.
- До получения первого полностью завершённого пакета не запускать новую волну авторов.
  Затем максимум два авторских пакета одновременно и одна независимая проверка;
  очередь ожидающих независимого ревью — не более двух пакетов. Сначала разгружать её.
- Новые чаты/сообщения — только при имеющейся авторизации. При разрешённом запуске:
  автор и механическая работа — GPT-6 Luna/medium; координатор и независимый читатель —
  GPT-6.1 Sol/medium. Не менять модель существующих чатов без отдельного основания.

## Что координатор передаёт исполнителю

Одно короткое поручение: цель, список ID, baseline commit, разрешённые пути,
ссылка на требования, индекс сохранённых источников, формат результата, проверка и критерий остановки.
Не передавать всю историю переписки, старые отчёты и полный checkpoint.
Рабочий пакет и промежуточный результат с самого начала находятся в устойчивом каталоге задачи;
единственная копия в /tmp запрещена. Существующие данные не переписывать при переносе.

Пример поручения автору:

> Проверь перечисленные ID по baseline SHA. Прочитай каждую карточку целиком: вопрос,
> четыре варианта с ключом, объяснение и четыре заметки; проверь первичные контексты,
> сложность и смысловые пересечения с релевантными соседями. Сохрани ID/topic/difficulty/key.
> Исправляй только содержательные или языковые дефекты, не переписывай удачный текст ради
> отличия от baseline. Верни patch и manifest: READY, FIX или HOLD по каждому ID.
> Для каждого решения дай конкретное основание и точный locator. Передай готовую часть,
> даже если остальные ID заблокированы. После одного адресного исправления спорные карточки
> вынеси в HOLD; не продолжай бесконечный поиск.

## Источники и доказательства

- Сначала открыть сохранённый первичный контекст по индексу; не скачивать его повторно
  только из-за нового исполнителя. Независимый читатель действительно читает контекст,
  а не наследует авторский PASS.
- Проверять утверждения всех вариантов и заметок. HTTP 200, hash и наличие URL доказывают
  получение файла, но не достоверность текста. Шаблонное «source supports note» не является основанием.
- На недоступный URL: одна ограниченная попытка плюс один официальный альтернативный путь.
  Неполный ответ, challenge, ошибка TLS/DNS или timeout — диагностический результат.
  Затем HOLD конкретного утверждения и точный запрос источника. Не обходить ограничения доступа.
- Общий полный первичный материал сохранять один раз с URL, датой, SHA и locator.
  В карточках — ссылки на этот материал и конкретные основания; не дублировать raw
  в каждом пакете/чате. Сохранность ранее требуемых полных контекстов не ослабляется.
- Существующие шесть групп полей, отдельные основания для вариантов/заметок и frozen hashes
  сохраняются. Формировать hashes и проверять схему инструментом, а не ручным переписыванием.
  Проза нужна для смысла решения, не для пересказа хэшей и маршрута Git.
- Никогда не засчитывать HOLD, structural-only, PASSready или авторский FIX как завершённый CURRENT.

## Независимая проверка и завершение

1. Автор сохраняет patch, точные before/after hashes и доказательства; READY/FIX отделяет от HOLD.
2. Координатор сверяет preimage с текущим файлом, применяет только разрешённые ID атомарно.
   Drift одного ID возвращает только этот ID на сверку; весь пакет заново не открывается.
3. Независимый читатель проверяет точный CURRENT целиком, первичные контексты и релевантных соседей.
   Его результат привязан к hash карточки и содержит конкретный PASS либо дефект.
4. На дефект допускается один адресный fix-cycle; после правки проверяется новая карточка
   и затронутые зависимости. Не перечитывать неизменившиеся другие карточки.
   Неразрешённый дефект — HOLD с владельцем следующего действия, не новое бесконечное поручение.
5. Координатор сопоставляет авторский и независимый результат, разрешает расхождения явно,
   проверяет инварианты/полноту и сохраняет commit. Зачёт увеличивается только для
   уникальных ID с доказанной актуальной версией и пройденными нужными проверками.
6. В checkpoint добавляется результат пакета. В основной записи остаются актуальные IDs,
   hashes, статусы и ссылки; история хранится в отдельных неизменяемых файлах.
   Не наращивать в одном JSON поля successor01..., coordinatorHistory и копии старых пакетов.
   Миграция старого checkpoint — отдельная работа, не ручное удаление истории.

## Проверки и критерии остановки

- До запуска выбрать affected checks по реальному diff. Для документации — ссылки/структура
  и git diff --check. Для контента — проверка схемы, уникальности ID, frozen key/difficulty,
  preimage/after hashes, полноты ссылок и затронутых контрактов каталога.
- Конкретные команды брать из текущего проекта после чтения их маршрута. Не запускать весь
  каталог, full QA, браузер, сборку или deploy «на всякий случай». Runtime QA, если нужен,
  только muted с самого старта. Автоматическая проверка не заменяет содержательное ревью.
- Через 30 минут без передачи хотя бы одной готовой карточки сохранить короткий checkpoint:
  что мешает, какие ID готовы, какое конкретное следующее действие. Это сигнал сменить маршрут,
  а не снизить требования к качеству или оборвать выполняющуюся обязательную проверку.
- Два одинаковых технических сбоя подряд: сохранить состояние, прекратить повторения
  неизменившегося вызова и сообщить конкретный блокер. Heartbeat не должен бесконечно будить
  сломанный координатор; возобновление требует изменения условия.
- После первого compaction сохранить текущий срез; после второго — только атомарное
  завершение, сохранение и остановка. Преемник получает manifest незавершённого среза,
  а не всю историю. Не создавать преемников ради повторного оформления тех же доказательств.
- wait_threads использовать с сохранённым cursor. Полный read_thread — только для нового
  результата, ошибки или перехода; большие ответы сначала фильтровать, не выводить в контекст.

## Финальное сообщение исполнителя

До 10 строк: scope/baseline; READY/FIX/HOLD по ID; конкретные дефекты; проверенные контракты;
пути результата; ветка и commit; что перенесено в main; следующий исполнитель/действие.
Указать, какие проверки не выполнены. Продолжение не должно требовать поиска файлов в /tmp.

Чат закрывается после сохранения результата и доказательств, проверки отсутствия своих процессов
и освобождения claim. Закрытие чата, завершение вопроса, merge, human acceptance и deploy
учитываются отдельно. Сессии старого процесса остановлены; этот документ сам их не перезапускает.
