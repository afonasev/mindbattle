# Ревизия вопросов: редакция 2026-10-25

Основание: поручение пользователя «давай исправим правила в проекте если нужно и инструкции кординатора», чат 01a173ad-84a8-7523-8177-930a3f773658. Scope: организация уже разрешённой exact2000 ревизии. Цель остаётся 2000 качественно проверенных вопросов.

## Приоритет и переход

Эта редакция явно заменяет противоречащие ей процедурные дополнения старых pinned process, method-pilot, packet-format и bootstrap/task prompts: exact-four literal calls, обязательный whole-output аудит всех tool results, повторное чтение неизменившихся политик, ручной пересчёт журналов и one-card-only scheduling. Она не отменяет содержательные требования этих документов и канонических GAME_SPEC/question-catalog, формат доказательств карточки и ограничения источников.

Координатор завершает уже начатый атомарный результат по его текущему контракту. Затем один раз записывает новую process revision и границу применения в своём существующем manifest, сохраняя ownership, CURRENT, hashes и указатели на историю. Не создавать отдельный migration-проект и не переписывать старые frozen artifacts. Новый порядок действует только для последующих поручений. Исторические FAIL/HOLD, израсходованные попытки и циклы не обнуляются; старые карточки автоматически не переоткрываются.

Для уже ожидающего READONLY ACK исполнителя координатор посылает одно явное START с этой редакцией, точными ID и границами записи. Это разрешённая пользователем смена процедурного контракта; ещё один bootstrap и запрос human GO не нужны. Действующие preservation-only/second-compaction STOP не снимаются. Передача ownership/lease по-прежнему отдельный проверяемый переход. Делегирование, новые чаты, сообщения, merge/deploy допустимы только в пределах имеющейся авторизации; изменение этой политики не расширяет её.

## Компактное поручение и доказательства исполнения

- Поручение: роль, 3 конкретных ID пилота одной темы, baseline, process revision, разрешённые пути, ссылки на content policy и сохранённые источники, формат результата и критерий остановки. Историю и полный checkpoint не копировать.
- Обязательные применимые правила прочитать один раз за revision. Независимые read-only вызовы объединять. Порядок вызовов, оболочка JavaScript, cat/sed/awk и количество outer calls не являются gates качества.
- Идентичность и ownership проверять один раз при назначении/переходе поддерживаемым инструментом и фактическим returned thread ID. Исходные вызовы/журналы сохраняются. Их ручная реконструкция нужна только при конкретном несовпадении, а не при каждом поручении.
- Технические проверки возвращают компактные PASS/FAIL, проверенные ID/revision и путь к полному результату. Проекция вывода не является дефектом, если необходимые факты доступны и полный результат сохранён. Недостающие исходные данные нельзя объявлять прочитанными: дочитать именно недостающий контекст.
- Автор и reviewer лично читают полный текст каждой назначенной карточки и необходимые полные контексты источников. Компактный технический вывод не заменяет содержательное чтение и не превращает чужой PASS в собственную проверку.
- Автоматизировать schema/hash/preimage/frozen-field/link checks существующими helpers; не строить новый универсальный audit framework в контентном цикле. Ошибка checker не равна дефекту карточки. Изолировать конкретную ошибку и её evidence; не повторять неизменившийся неуспешный вызов более двух раз. Неподтверждённый gate остаётся открытым для затронутых ID, остальные могут продвигаться.

## Работа пакетами без общего барьера

- Первый пилот — до 3 ещё не обработанных ID одной темы. Одна карточка остаётся атомарной единицей применения, вердикта и зачёта; пакет — единица поручения и повторного использования контекста.
- Максимум 2 активных авторских пакета, 1 независимый reviewer и 2 пакета в очереди READY. Это потолок, а не требование создавать новых исполнителей. Использовать действующие разрешённые чаты и модели.
- Автор предварительно проверяет наличие сохранённого контекста/доступность источников и обрабатывает ID по очереди. Готовые карточки передаёт сразу; HOLD одного ID не задерживает остальные. Предварительный поиск входит в тот же лимит попыток конкретного claim, не создаёт новый бюджет.
- Сохранённые источники переиспользовать по индексу. При недоступности остаётся прежний лимит: одна попытка и одна официальная альтернатива, затем HOLD конкретного claim. Никаких обходов доступа, третьего источника для исчерпанного claim или сброса истории через новое имя/чат.
- Независимый reviewer проверяет каждый ID, не выборку. До применения сверить preimage; до зачёта independent verdict должен соответствовать точному CURRENT/hash и должны пройти минимальные affected checks. Порядок INITIAL/apply сохранять по действующему content contract; нельзя зачесть неприменённое предложение.
- На содержательный дефект — один адресный fix-cycle и FINAL того же reviewer по новой версии и затронутым зависимостям. Сохранять уже израсходованные циклы. Неустранённый дефект — HOLD с причиной/следующим действием; третьей полной ревизии нет.
- Координатор сверяет evidence детерминированно, не повторяет полную содержательную проверку. QA для общего diff можно объединить, сохраняя связь результата с каждым точным ID/hash. READY, bootstrap и структурный PASS дают ноль зачтённых вопросов.
- После пилота при сохранённом качестве и достаточном контексте допустим пакет 5–10 ID. Это не отменяет compaction fences: насыщенный исполнитель завершает только разрешённый уже начатый атомарный результат и передаёт остальные ID без повторной обработки.

## Учёт результата и остановок

Использовать проекцию существующего manifest/checkpoint по [context-efficiency.md](context-efficiency.md), не второй статусный реестр. Показывать компактно: process revision, текущие ID/этап, accepted delta, HOLD с конкретными причинами, следующий шаг, ссылки на evidence. Все прежние raw evidence сохранять по ссылкам, не тащить в каждый handoff.

На первом пилоте измерить elapsed time, число реально зачтённых ID, HOLD, содержательные и процедурные возвраты, время bootstrap/ожидания/проверки. Токены учитывать только если runtime их сообщает; неизвестное — null, cached/uncached не смешивать. Не обещать ускорение без сравнения. Низкое число HOLD само по себе не показатель качества.

Через 30 минут без нового готового результата диагностировать одно узкое место и изменить следующий шаг в разрешённых пределах. Не прерывать обязательную проверку, не снижать quality gates, не начинать очередной аудит всей истории. При неизменном blocker ждать события/изменения условия, не генерировать ACK/status snapshots. Существующие wait cursors и компактный handoff сохраняются.
