# Контекст текущего среза

Читай для длинной задачи, batch-работы, после первого compaction или перед handoff.

- Один согласованный change/связный проверяемый срез — одна исполнительная сессия. Follow-up оставляй в ней, пока результат не завершён; независимая фича получает новый scope. Новый пользовательский чат создавай только по его явному запросу.
- После первого compaction запиши scope, уже проверенные факты и оставшиеся обязательные проверки. После второго не начинай следующий срез, новый batch или соседний цикл исследования; заверши текущий атомарный срез, начатые обязательные проверки, commit и handoff. Не прерывай проверку только ради счётчика.
- Handoff: цель/change ID, branch/SHA и spec revision, сделано и проверено, следующий конкретный шаг, blocker/вопрос, принадлежащие ресурсы и ссылки на evidence. Не копируй историю, логи или выполненные чеклисты целиком; не теряй ownership.
- Читай только skill текущей фазы и reference с подходящим триггером. Не перечитывай неизменившийся файл в одном срезе. Объединяй независимые read-only вызовы, фильтруй результаты до вывода модели.
- Полные логи и evidence сохраняй вне переписки. Проверки повторяй после относящейся к ним правки, новой ошибки или обязательного gate. Существующие release/visual/audio/device/human gates не ослабляй.
- Понятные ограниченные задачи разработки и сводки — GPT-6 Luna/medium; сложный scope — по model-routing. Не создавай подагента только ради короткой сводки. Пакеты дели только при разрешённом делегировании; родитель проверяет возвращённые факты.


## Сохраняемые дополнительные правила проекта

# Экономия контекста

Прочитай этот файл для длинной задачи, batch-генерации или после первого compaction.

- Оставляй follow-up в текущей задаче только пока он относится к той же незавершённой фиче. После проверки и коммита закрой текущий scope. Следующую фичу начинай отдельно; новый пользовательский чат требует явного запроса пользователя.
- Объединяй независимые read-only проверки. Возвращай сводку, ошибки и нужное доказательство, а не полные логи.
- Загружай только OpenSpec skill, относящийся к текущей фазе; не перечитывай неизменившиеся спецификации без причины.
- Для локального плейтеста используй in-app Browser. Chrome нужен только для существующей авторизации или состояния расширений.
- После второго compaction не расширяй scope: заверши текущий проверяемый срез и сохрани handoff. Создание нового чата требует существующей авторизации.
- Для browser QA держи один dev-сервер и origin; где возможно, собирай DOM, screenshot и console одним вызовом. Не ослабляй approval/guardian-проверки ради экономии.
- Пакетную генерацию контента дели на ограниченные независимые subagent-задачи с GPT-6 Luna/medium для понятных ограниченных задач. После compaction не продолжай такой пакет цепочкой follow-up: новый пакет начинай отдельно, а основной агент проверяет выборку и итог.


## Компактный вход и размер среза (решение 2026-10-19)

- Вход начинается с одного manifest: change/ID, текущая revision и hashes, ownership/границы записи, текущая стадия, действующие запреты, ссылки на evidence, один следующий шаг и критерий его завершения. Полный checkpoint и историю открывай только для конкретного расхождения; большой JSON сначала фильтруй по нужным полям.
- Не создавай второй источник статуса: manifest — компактное представление существующей актуальной записи или указатель на неё. Историю и полные доказательства сохраняй по ссылкам, не копируй в поручение и ответы.
- Исполнительный срез — один проверяемый результат; для редакторского конвейера начни с одной карточки на содержательный цикл. Следующую бери только после завершения текущей при достаточном контексте. Передача роли нужна при действительной смене ownership или остановке, а не после каждой карточки.
- После первого compaction сократи оставшийся срез до уже начатого результата и не загружай соседние пакеты. После второго соблюдай установленную остановку: только разрешённое завершение атомарного среза, необходимые проверки, сохранение и handoff. Более строгий preservation-only fence текущего исполнителя сохраняется.
- Не перечитывай неизменившийся pinned process, manifest и evidence в одном срезе. При расхождении сначала установи новую revision. Неизменившиеся cursor/blocker не требуют ACK, нового статусного сообщения или перезаписи snapshot.
- Эффект оценивай на одном тематическом пакете: accepted IDs/час, uncached input и output на принятый ID, bootstrap tokens/time, compactions и передачи ownership; отдельно форматные и содержательные возвраты. Не обещай экономию до измерения.
