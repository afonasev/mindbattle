# mindbattle — рабочие правила

## Запуски без звука (решение пользователя 2026-10-13)

- Если запуск не предполагает тестирование человеком, запускай игру, Unity Editor/Player, browser playtest и любые автоматические проверки без звукового вывода с самого старта. Это относится также к UI/visual QA, симуляциям, замерам производительности и автоматическим аудиотестам.
- Для Unity используй `-noaudio`; когда необходимо, дополнительно применяй временное QA-only отключение аудио проекта с восстановлением настроек после проверки. Для браузера отключай звук игры/вкладки до autoplay и начала теста. Одного `AudioListener.volume=0` после запуска недостаточно.
- Проверка аудиологики автоматикой не разрешает слышимый звук: используй offline/file-проверку или отключённый вывод на устройство, сохраняя тестовый контракт. Если выбранный тихий режим не позволяет выполнить проверку, запиши её как NotRun с причиной, не подменяй результат успешной проверкой.
- Звук допускается только для запуска, который предусматривает тестирование человеком, в пределах запрошенного теста и с учётом явного требования пользователя о тишине. Автоматический запуск для подготовки такого теста остаётся без звука до человеческой проверки.
- Не меняй системную громкость и не затрагивай звук чужих приложений. Это правило заменяет прежние исключения «включать звук, если тест касается аудио» для автономных запусков и действует во всех ветках/worktree проекта.

- Planning и `docs/GAME_SPEC.md`: shared root из `workflow/project.json`, store `mindbattle-planning`; локальный GAME_SPEC — указатель.
- Явное решение пользователя имеет приоритет. Сохраняй утверждённые требования, exact scope, историю и чужую незакоммиченную работу; новые продуктовые развилки согласуй до реализации.
- Изменения выполняй в принадлежащем задаче Git worktree/ветке. Не возобновляй другой change автоматически. Не выдавай автоматические проверки за human/device/visual/audio acceptance; deploy/archive требуют существующей авторизации и gates.
- Ищи сначала `rg --files`, затем узким `rg -n`; соблюдай gitignore, не сканируй generated/Library/build/dist/logs и бинарные ассеты без необходимости. Читай только нужные диапазоны.
- Понятная ограниченная разработка: **GPT-6 Luna/medium**. Сложный scope и архитектура — по `.agents/references/model-routing.md`; явный model/effort пользователя важнее профиля. Делегирование не обязательно для каждого патча.
- После второго compaction — только завершение текущего среза, уже нужные проверки, commit и короткий handoff; затем остановись. Подробности `.agents/references/context-efficiency.md`.
- Координатор ждёт события завершения/вмешательства через `wait_threads` с `timeoutMs: 120000` и `afterCursor`; неизменившийся таймаут не повод перечитывать чат. Подробности `.agents/references/coordination.md`.

Подробные правила вынесены без отмены требований. Загружай только строку с подходящим триггером; не читай все references при старте и не перечитывай неизменившееся в одном срезе.

## Завершение конкретной сессии (решение пользователя 2026-10-11)

- В финальном ответе явно напиши: «Сессию можно архивировать без потери данных», если в этой сессии больше действий не планируется, работа и нужные доказательства сохранены в Git/устойчивом хранилище, ресурсы освобождены, а продолжение не зависит от несохранённых файлов, процессов или контекста только этого чата. Укажи commit/ветку или путь сохранения, когда это нужно для продолжения.
- Если работа ещё требует действия, явно напиши «Следующий шаг: …»: конкретное действие, кто его выполняет (агент или человек), ожидаемая команда/решение и сохранённая точка продолжения. Если архивировать пока нельзя, назови конкретную причину и что нужно сохранить или завершить; не оставляй неопределённое «готово».
- Архивирование чата, человеческая приёмка результата, merge, build и deploy — отдельные действия. Рекомендация архивировать чат не подменяет незакрытые gates и не разрешает автоматически архивировать OpenSpec change, публиковать результат или удалять несохранённую работу.
