## MODIFIED Requirements

### Requirement: Сервер предоставляет агрегированную сводку фидбэка
Система SHALL строить read-only сводку v3 по каждому questionId и назначенной difficulty: число показов, количество жалоб, количество отсутствия жалоб и количества каждой причины. Сводка MUST показывать v1, v2 и v3 отдельно, не MUST автоматически переклассифицировать каталог и MUST исключать текст заметок из числовых агрегатов. Повреждённые строки журнала MUST не включаться в агрегаты и SHALL быть отражены счётчиком диагностических ошибок. Сводка, raw NDJSON-журнал и свободные заметки MUST быть доступны только оператору production-сервера через SSH или локальное выполнение отчёта; HTTP origin MUST не предоставлять endpoint для их чтения, выгрузки или агрегирования.

#### Scenario: Сравнение сложности с контекстом темы
- **WHEN** для вопроса записаны девять результатов без жалобы и одна жалоба `too-hard`
- **THEN** SSH-отчёт показывает десять показов, одну жалобу, девять отсутствий жалобы и одну отметку `too-hard`

#### Scenario: Сигналы качества вопроса
- **WHEN** редактор читает локальный NDJSON-журнал для разбора жалоб через SSH
- **THEN** он может увидеть заметку только в полной v3-записи без связи с командой, игроком или игровым ответом

#### Scenario: Пустой журнал
- **WHEN** ещё не сохранено ни одного события
- **THEN** SSH-отчёт возвращает нулевые агрегаты и нулевой счётчик повреждённых строк

#### Scenario: Запрос публичной аналитики
- **WHEN** посетитель production origin запрашивает прежний или иной HTTP endpoint чтения feedback-журнала либо его агрегатов
- **THEN** origin отвечает `404` и не раскрывает число событий, причины, заметки или путь к файлу

## ADDED Requirements

### Requirement: Production-журнал объединяет анонимные события с разных устройств
Production runtime SHALL принимать валидные v3-события от browser-клиентов, открытых на разных устройствах через один same-origin `POST`, и MUST записывать их в один серверный append-only журнал вне web-root. Успешно записанное событие MUST оставаться доступным SSH-отчёту независимо от localStorage, браузера или устройства, с которого оно было отправлено. Система MUST не добавлять аккаунты, device identifier, IP-адрес, игровые ответы, teamId или счёт в событие либо агрегат.

#### Scenario: Два независимых устройства
- **WHEN** два browser-клиента на разных устройствах отправляют разные валидные v3-события в production origin
- **THEN** каждое событие один раз присутствует в общем серверном журнале и учитывается одним SSH-отчётом без идентификатора устройства

#### Scenario: Повтор после локальной ошибки
- **WHEN** browser-клиент не получает подтверждение записи и повторяет сохранённое локально событие с тем же eventId
- **THEN** сервер не создаёт дубликат, а после успешного подтверждения событие включается в общий SSH-отчёт
