## Purpose

Определяет единый общий выбор воспринимаемой сложности после каждого вопроса, надёжную локальную серверную запись без персональных данных и проверяемую сводку для последующей редакторской переклассификации каталога.

## ADDED Requirements

### Requirement: После каждого вопроса собирается одна общая оценка
Система SHALL запрашивать ровно одну общую оценку easy, medium или hard после раскрытия и объяснения каждого обычного, бонусного и tie-break-вопроса. Оценка MUST не менять очки, время, состав претендентов, текущую сложность вопроса, shuffle-bag или содержание последующих партий.

#### Scenario: Компания согласовала оценку
- **WHEN** любой назначенный контроллер выбирает один из трёх уровней после neutral gate
- **THEN** система фиксирует один консенсусный выбор для показанного вопроса и блокирует дополнительные голоса

#### Scenario: Неоценённый вопрос
- **WHEN** оценка ещё не подтверждена сервером
- **THEN** система не переходит к следующему игровому экрану и не запускает игровые часы

### Requirement: Событие оценки минимально и идемпотентно
Клиент SHALL отправлять версионированное событие с уникальным eventId, непрозрачным matchId, catalogRevision, questionId, назначенной каталогом difficulty и выбранной perceivedDifficulty. Событие MUST не содержать имена, идентификатор команды, ответы команд, счёт, свободный текст или данные устройства.

#### Scenario: Первая запись события
- **WHEN** API получает валидный ранее не встречавшийся eventId
- **THEN** сервер один раз записывает событие, добавляет серверное время и подтверждает создание

#### Scenario: Повтор того же события
- **WHEN** API повторно получает тот же eventId с тем же содержимым
- **THEN** сервер не добавляет вторую строку и возвращает успешное идемпотентное подтверждение

#### Scenario: Конфликт eventId
- **WHEN** ранее записанный eventId приходит с другим содержимым
- **THEN** сервер отклоняет запрос как конфликт и не изменяет файл

#### Scenario: Невалидное событие
- **WHEN** отсутствует обязательное поле, уровень не входит в easy/medium/hard или questionId не существует в текущем каталоге
- **THEN** сервер отклоняет запрос с диагностикой и не изменяет файл

### Requirement: Сервер хранит append-only NDJSON-журнал
Локальный сервер SHALL последовательно дописывать каждое подтверждённое событие отдельной UTF-8 JSON-строкой в файл по конфигурируемому пути и MUST обеспечивать валидные границы строк при конкурентных запросах. Родительский каталог SHALL создаваться при запуске, а существующие валидные события SHALL сохраняться между перезапусками.

#### Scenario: Конкурентные разные события
- **WHEN** почти одновременно поступают несколько валидных событий с разными eventId
- **THEN** каждое событие присутствует в журнале ровно один раз как отдельная разбираемая JSON-строка

#### Scenario: Ошибка записи
- **WHEN** файл нельзя открыть, создать или дописать
- **THEN** сервер не подтверждает событие, клиент сохраняет экран оценки и предлагает повторить отправку

#### Scenario: Восстановление ожидающей оценки
- **WHEN** приложение перезапущено со снимком партии, ожидающим подтверждения оценки
- **THEN** оно восстанавливает тот же eventId и выбранное значение и может безопасно повторить отправку

### Requirement: Сервер предоставляет агрегированную сводку
Система SHALL предоставлять read-only сводку по каждому questionId и по назначенной difficulty: общее число оценок, количества perceived easy/medium/hard, долю совпадений и количества оценок ниже или выше назначенного уровня. Повреждённые строки журнала MUST не включаться в агрегаты и SHALL быть отражены счётчиком диагностических ошибок.

#### Scenario: Сравнение сложности
- **WHEN** запрошена сводка после нескольких игр
- **THEN** ответ позволяет определить, сколько оценок совпало с каталогом, оказалось легче и оказалось сложнее редакторского уровня для каждого вопроса и уровня в целом

#### Scenario: Пустой журнал
- **WHEN** ещё не сохранено ни одной оценки
- **THEN** сервер возвращает нулевые агрегаты и нулевой счётчик повреждённых строк
