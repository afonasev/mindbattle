## Context

См. мотивацию в `proposal.md`. Сейчас каталог содержит 30 × 30 вопросов и по десять элементов в каждом difficulty-bag. Чистое доменное ядро заканчивает вопрос фазой `reveal`, после чего команда `continue` сразу ведёт к следующему игровому состоянию. Browser-клиент полностью статический, а `localStorage` хранит единственный snapshot и историю повторов; разрешённых runtime-запросов и серверного процесса нет.

Change одновременно меняет контентную модель, сериализуемый поток партии, общий физический ввод, браузерный UI и локальную persistence-границу. Утверждённая топология остаётся локальной: 2–4 команды и один общий экран на одной машине. Node runtime является техническим спутником этой локальной сессии, а не сетевым мультиплеером.

## Goals / Non-Goals

**Goals:**

- Сохранить идентичность и редакторский след 900 существующих вопросов при переклассификации и добавить 600 действительно базовых easy-вопросов.
- Сделать оценку обязательной частью сериализуемого потока после каждого вопроса без влияния на игровые правила и competitive outcome.
- Подтверждать переход только после долговечной идемпотентной записи в локальный серверный файл.
- Собирать минимальные данные, достаточные для последующего сравнения assigned и perceived difficulty.
- Сохранить чистую границу домена: правила не импортируют HTTP, filesystem, React или физический ввод.

**Non-Goals:**

- Автоматически менять difficulty каталога по голосам или влиять ими на текущую/следующую партию.
- Делать отдельные голоса команд или игроков, определять большинство, хранить личности либо свободный комментарий.
- Проектировать production-хостинг, удалённую базу, аккаунты, синхронизацию нескольких машин или публичную аналитику.
- Менять длину партии, очки, таймеры, тему, бонусы, правила tie-break или количество команд.
- Добавлять dashboard аналитики в игровой клиент: первая версия предоставляет машиночитаемую серверную сводку.

## Decisions

### 1. Каталог становится 20 easy / 10 medium / 20 hard на тему

В каждый из 30 пакетов добавляются 20 новых easy-вопросов. Все прежние easy сохраняют ID и содержимое, но получают medium; прежние medium получают hard; прежние hard остаются hard. Получается 50 вопросов на тему и 1500 всего.

Выбран этот вариант, потому что easy расходуются первыми и многие короткие партии не доходят до поздних этапов. Рассматривались 10 новых easy (меньше разнообразия) и четвёртая expert-категория (меняет профиль партии); оба варианта отклонены пользователем или выходят за scope.

Служебный `starter`-hotfix больше не нужен: первый этап использует весь новый easy-pool из 20 вопросов. Перед интеграцией каждого пакета валидатор проверяет квоту 20/10/20, а независимый агент проверяет новые факты, варианты, источники и соответствие порогу общеизвестности. Review хранит хэш полного нового пакета.

Источник перестаёт быть только служебным полем: reveal-view передаёт его renderer вместе с объяснением, а DOM показывает после пояснения подписанную внешнюю ссылку. Клиент не делает автоматический запрос к источнику; переход происходит только по явному клику, в новой вкладке с изоляцией `noopener/noreferrer`, поэтому офлайн-партия и основной игровой поток от доступности внешней страницы не зависят.

### 2. История вопросов мигрируется по questionId, а не сбрасывается

Новая ревизия каталога делает старый незавершённый snapshot несовместимым, но частота и давность показов существующих questionId сохраняются. Мигратор собирает `shownCount`, `lastShownSerial` и последний показ по ID из прежних bags, распределяет существующие ID в bags новой difficulty и очищает `remaining`/`previousOrder`, чтобы следующий порядок был построен заново. Новые easy начинаются как unseen.

Это избегает немедленных повторов старого контента и одновременно не пытается переносить порядок bag между множествами разного размера. Полный сброс истории проще, но нарушает утверждённую защиту от ранних повторов.

### 3. Между reveal и continuation появляется сериализуемая feedback-фаза

Первое новое нажатие после neutral gate закрывает чтение reveal и переводит ядро в `difficulty-feedback`. Фаза хранит ссылку на завершённый раунд, прежний `continuation`, стабильный `eventId` и `selectedDifficulty: null | easy | medium | hard`.

Любой назначенный контроллер после второго neutral gate может отправить семантическую команду `rate-difficulty`. Первая команда фиксирует общий выбор; остальные игнорируются. Application controller сохраняет snapshot, вызывает feedback adapter и только после успешного acknowledgement отправляет доменную команду `confirm-difficulty-feedback`, которая применяет сохранённый continuation. При ошибке выбранное значение остаётся в snapshot, UI показывает retry, а повтор использует тот же eventId.

Домен знает только факт выбора и подтверждения конкретного eventId, но не HTTP или файл. I/O-статусы `pending/error` принадлежат application/UI и не участвуют в правилах. При восстановлении snapshot с уже выбранной, но не подтверждённой оценкой controller безопасно повторяет POST.

Автоматический переход сразу из reveal в оценку отклонён: он сокращает время чтения объяснения. Переход к следующему игровому экрану до server acknowledgement отклонён: при закрытии вкладки оценка могла бы остаться только в браузере, что противоречит цели change.

### 4. eventId стабилен, а payload минимален

При создании партии application передаёт ядру непрозрачный `matchId`, созданный тем же источником уникальных seed/ID и сохраняемый в snapshot. Для каждого завершённого вопроса ядро формирует стабильный eventId из версии схемы, matchId, режима/порядкового номера вопроса и questionId. Одинаковое состояние всегда даёт одинаковый ID, а новый матч — другой.

Payload содержит только `schemaVersion`, `eventId`, `matchId`, `catalogRevision`, `questionId`, `assignedDifficulty` и `perceivedDifficulty`. Сервер добавляет `recordedAt`. Ответы, очки, teamId, device ID, IP в журнале приложения, свободный текст и имена не сохраняются.

### 5. Одна позиционная схема для общего выбора

Экран показывает три горизонтально читаемых действия: слева «Легко», сверху/в центре «Средне», справа «Сложно». Им соответствуют A/W/D, ←/↑/→ и face-west/north/east; подсказки объединяют все назначенные схемы и не используют командные цвета. Нажатие вниз игнорируется.

Это повторяет уже знакомую прямую позиционную схему трёх обычных тем. Отдельное подтверждение отклонено как лишний шаг; командные голоса отклонены, потому что пользователь утвердил один совместно согласованный ответ от всей компании.

### 6. Same-origin Node API и append-only NDJSON

Локальный Node runtime по умолчанию слушает только loopback-интерфейс, обслуживает browser bundle и два same-origin endpoint:

- `POST /api/difficulty-feedback` — валидация, дедупликация и запись события;
- `GET /api/difficulty-feedback/summary` — read-only агрегаты по questionId и assigned difficulty.

Путь журнала задаётся конфигурацией, по умолчанию `data/difficulty-feedback.ndjson` относительно проекта/runtime data directory. CORS не включается, размер JSON ограничивается небольшим верхним пределом, questionId и assignedDifficulty сверяются с текущим каталогом.

При старте сервер последовательно читает журнал, строит индекс `eventId → canonical payload` и агрегаты. Невалидные строки пропускаются с диагностическим счётчиком. Если файл не заканчивается переводом строки, сервер отделяет следующий append новым переводом, сохраняя повреждённый хвост как самостоятельную диагностируемую строку.

Записи проходят через единую promise-очередь: canonical JSON-строка дописывается, file handle синхронизируется, затем обновляются индекс/агрегаты и отправляется acknowledgement. Тот же ID и payload возвращает idempotent success; тот же ID с иным payload — conflict. Файловая БД рассматривалась, но для локального прототипа NDJSON лучше отвечает требованию прозрачного файла и простого последующего анализа.

### 7. Сводка считает направление расхождения по порядку уровней

Для агрегации используется порядок easy = 0, medium = 1, hard = 2. `perceived > assigned` означает «игрокам было сложнее редакторской оценки», `perceived < assigned` — «игрокам было легче». Сводка возвращает total, матрицу perceived counts, exact/lower/higher counts и доли для каждого questionId и каждого assigned level, плюс число повреждённых строк.

Сводка вычисляется из серверного журнала/индекса и не влияет на runtime-каталог. Порог автоматического переноса намеренно не задаётся: это отдельное продуктовое решение после накопления данных.

## Risks / Trade-offs

- [600 новых вопросов могут иметь неравномерный фактический порог easy] → единый редакторский checklist, источники, независимый review каждого тематического пакета и последующая серверная обратная связь.
- [Обязательная оценка удлиняет каждый вопрос] → один общий выбор без командного голосования, таймера и дополнительного подтверждения.
- [Недоступный или unwritable файл останавливает переход] → явная диагностика пути, retry на том же экране, идемпотентный eventId и проверка writeability при запуске сервера.
- [Повторный POST после неопределённого сетевого исхода] → дедупликация до append и успешный ответ на точный duplicate.
- [Повреждение последней строки после аварийного завершения] → `sync` до ack, изоляция незавершённого хвоста и диагностический счётчик при чтении.
- [Локальный API увеличивает сложность запуска и отменяет полностью статический runtime] → единая документированная команда запуска, same-origin topology и отсутствие внешних сервисов.
- [Старый snapshot несовместим с новой ревизией] → сохранить историю показов по ID, безопасно отбросить только незавершённый match snapshot и явно сообщить это в migration note.
- [Несколько одновременных контроллеров создают гонку] → детерминированный порядок входных действий в кадре; принимается первая валидная команда, остальные игнорируются.

## Migration Plan

1. Обновить `docs/GAME_SPEC.md` и журнал решений: каталог 1500, общий feedback-шаг, локальный Node API и исключение из прежнего запрета backend/runtime-запросов.
2. Удалить временный `starter`-механизм, перенести difficulty 600 существующих вопросов без изменения ID и мигрировать историю по questionId.
3. Подготовить и независимо проверить 600 новых easy-вопросов, затем выпустить новую catalog revision.
4. Добавить feedback-фазу, UI/ввод и server adapter за feature-complete тестами.
5. Добавить Node runtime, NDJSON store, summary API и integration tests с временным data path.
6. Выполнить unit/content/build/browser проверки и локальный плейтест с несколькими реальными контроллерами; проверить фактические строки и сводку после обычного, бонусного и tie-break-вопросов.
7. Доставить всё одним отдельным commit после `openspec validate --strict` и проверки точного staged scope.

Rollback к прежней версии клиента не удаляет NDJSON-файл; он остаётся читаемым артефактом. Новая ревизия каталога и несовместимый snapshot откатываются вместе с кодом, а сохранённая до миграции история должна быть предварительно скопирована тестом миграции.
