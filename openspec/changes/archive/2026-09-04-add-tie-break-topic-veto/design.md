## Context

См. [proposal.md](proposal.md). Сейчас `tie-break` непосредственно выбирает случайный hard-вопрос без темы, а бонусная фаза уже реализует нужную модель N+1 публичных запретов и нейтрального ввода. Авторитетное состояние, snapshot и UI отличают бонусную подготовку только косвенно по индексу основного вопроса, поэтому финал требует явного контекста выбора.

## Goals / Non-Goals

**Goals:**

- Сделать выбор финальной темы воспроизводимым, сериализуемым и доступным только текущим претендентам.
- Переиспользовать правило разных запретов и трёхсекундную авторитетную подготовку без утечки бонусного множителя или текста.
- Сохранить deterministic replay, neutral gate, паузу и восстановление snapshot.

**Non-Goals:**

- Не менять profile `classic-v1`, очки, вопросный таймер, запас времени, правила ответов, определение победителя, фидбэк, аудио или сетевую топологию.
- Не добавлять новую случайность после того, как претенденты оставили тему, и не давать зрителям влияние на финал.

## Decisions

### 1. Отдельная финальная veto-фаза в авторитетном состоянии

Domain вводит дискриминированную фазу финального выбора с `candidates`, `cursors`, `vetoes` и зафиксированным составом претендентов из `tieBreak`. Она создаётся перед каждым вопросом tie-break, используя тот же контракт topic-selector: N+1 тем, `hard`, исключение уже выбранных тем и обновлённый seeded state. Только события от `tieBreak.contenders` меняют эту фазу.

Отдельная фаза предпочтительнее переиспользования `bonus-veto`: она не позволяет UI, selectors или сериализации выводить бонусность из номера основного вопроса и исключает случайную подмену финальной темы бонусным поведением.

### 2. Подготовка хранит назначение вопроса явно

Подготовительная фаза несёт режим последующего вопроса (`main` или `tie-break`) и presentation-kind (`normal`, `bonus`, `final`). После N разных запретов она сохраняет оставшуюся тему, запускает ровно 3 000 ms и по истечении или после neutral-gated continue вызывает выбор hard-вопроса этой темы в `tie-break`-режиме. И `points`, и multiplier остаются нулевыми по уже существующему tie-break-контракту.

Альтернатива — вычислять presentation-kind по `mainQuestionIndex` — отвергнута: в финале индекс не меняется и это вернуло бы неверную обычную или бонусную маркировку.

### 3. Очередной финальный список строится после фидбэка

После reveal и обязательного фидбэка существующая continuation определяет нового победителя, тот же состав при отсутствии верных ответов либо суженный состав верных. Только затем начинается новый финальный список тем. Это сохраняет уже утверждённую границу фидбэка и не создаёт два параллельных вопросных перехода.

### 4. Сохранение и input следуют фазе, а не UI

Serialization валидирует конечность списка, принадлежность курсоров и запретов текущим претендентам, уникальность полных запретов и связность `tieBreak`. Snapshot во время финальной подготовки хранит её mode/presentation-kind и остаток времени. Input layer переводит физические действия в такие же семантические veto-команды, но domain окончательно проверяет право участника. React только отображает селектор и «Финальная тема».

Локальная сессия остаётся единственным поддержанным способом игры: минимум — две активные команды; blur и отключение контроллера продолжают ставить партию на паузу, а переподключение не изменяет запреты.

## Risks / Trade-offs

- [Смешение финальной и бонусной презентации] → явный `presentation-kind`, отдельные selector/UI-тесты и запрет `x2`/бонусного текста на финальном экране.
- [Некорректный переход после удержанного запрета] → existing neutral gate применяется к новой фазе, а domain прекращает обработку frame при смене фазы.
- [Исчерпание допустимых hard-тем] → selector диагностирует это до изменения snapshot; не выбирает случайную тему в обход правил.
- [Старый snapshot не распознаёт новую фазу] → schema-version migration структурно добавляет новую discriminated phase либо безопасно отклоняет повреждённый snapshot.

## Migration Plan

1. Обновить канонический GAME_SPEC и OpenSpec delta-specs.
2. Расширить domain types, выбор тем/вопросов, transitions, selectors и snapshot validation/migration.
3. Адаптировать controller input, UI и стили; убрать поясняющую фразу о старте вопроса из всех topic-confirmation экранов.
4. Добавить unit-тесты равных/неполных запретов, сужения претендентов, отсутствия очков, pause/restore и невалидного ввода зрителя; обновить browser-тесты и сделать muted QA.
5. Выполнить strict OpenSpec validation, проектные проверки и реальный локальный плейтест минимум двух команд с разными схемами управления.

Rollback — Git revert единственного change-коммита; snapshot неизвестной новой фазы безопасно не возобновляется.
