## Context

См. `proposal.md` — Why. Репозиторий уже имеет offline-first React/Vite foundation с разделёнными entrypoint-границами и проверкой отсутствия browser-зависимостей в `domain`. Change добавляет всё состояние партии, нативный ввод, локальное сохранение, 900 статических вопросов и законченный DOM/CSS-поток на одном desktop Chromium-экране.

Главные ограничения: правила должны быть детерминированными и сериализуемыми; физический ввод и монотонное время приходят командами снаружи; скрытые ответы не должны попадать в публичную UI-проекцию; одно устройство нельзя назначить двум командам; внешняя сеть и runtime-сервисы запрещены.

## Goals / Non-Goals

**Goals:**

- Сделать чистое ядро, которое одинаково воспроизводит партию из seed, каталога и упорядоченных input-frame.
- Дать React только публичные projections и semantic commands, а adapters — браузерные часы, устройства, storage и audio.
- Разделить контент на независимо генерируемые и проверяемые тематические JSON-пакеты.
- Проверить клавиатурный multiplayer в реальном Chromium и оставить честный ручной gate для физических gamepad.

**Non-Goals:**

- Replay-файл, сетевой протокол, серверная авторитетность, PWA/desktop packaging и история нескольких партий.
- Произвольные пользовательские правила или редактор вопросов внутри клиента.
- Canvas/WebGL, полноценная озвучка и постоянная музыка.

## Decisions

### 1. Чистый reducer обрабатывает атомарные input-frame

`src/domain` владеет `MatchState`, `DomainCommand`, `reduceFrame(state, frame, context)` и публичными selectors. `InputFrame` содержит монотонный `atMs`, последовательность и упорядоченный список команд; reducer сначала доводит часы, затем применяет допустимые команды кадра и выполняет автоматические переходы. Несколько ответов одного кадра применяются до проверки завершения, поэтому последняя отвечающая команда не лишает другую команду одновременного изменения.

Альтернатива с React state/XState отклонена: она привязала бы авторитетные правила к UI runtime и усложнила бы детерминированные тесты и snapshot.

### 2. Фазы — discriminated union, пауза — ортогональный overlay

Фазы: `normal-topic`, `bonus-veto`, `answering`, `reveal`, `standings`, `finished`. Tie-break хранит исходных лидеров и текущее множество претендентов; зрительские команды остаются в общей таблице, но не допускаются к ответу. Пауза хранит причины отдельно, после нормализации часов ставит временной anchor в `null`, а resume создаёт новый anchor.

Так не нужны дубли всех фаз `paused-*`, а JSON round-trip остаётся прямым.

### 3. Баланс и время выводятся из валидируемого classic-v1

`classic-v1` — immutable-конфигурация: длины, stage-size, сложности, очки, множитель, допустимое базовое время и reserve. Ядро не принимает произвольный запас. На каждом кадре elapsed сначала расходует общий base, остаток — независимо reserve команд со статусом `open`. Ответ на точной границе base при нулевом reserve уже не принимается; при положительном reserve ещё возможен.

Альтернатива с UI interval как источником истины отклонена из-за drift и паузы.

### 4. PRNG и планировщик передают сериализуемое состояние

Используется небольшой явный seeded PRNG без `Math.random`. Он определяет первого chooser, перестановки тем, option order и question bags. Для каждой `topic × difficulty` история хранит текущий цикл/остаток, последнюю границу и счётчики давности; после исчерпания строится другая перестановка, не повторяющая предыдущую целиком и boundary-question.

Внутри партии хранится множество выбранных тем и показанных вопросов. Показанные, но не выбранные темы получают penalty при следующем формировании вариантов, а равные кандидаты перемешиваются PRNG — поэтому история не создаёт постоянный порядок.

### 5. Каталог собирается из 30 независимых JSON

Каждый `src/content/topics/<topic-id>.json` содержит метаданные темы и 30 записей. Build-time loader формирует typed catalog; validator проверяет JSON schema, квоты, уникальность IDs/вариантов, один correct index, длину explanation, 2–4 предложения, источник, дату и временной контекст. Отдельный manifest фиксирует автора/проверяющего пакета и статус ревью.

Это позволяет агентам работать по непересекающимся файлам пакетами тем и затем проводить перекрёстное ревью. Один огромный JSON отклонён из-за конфликтов и высокой стоимости повторного контекста.

### 6. Input adapter выдаёт только semantic actions и rising edge

WASD и Arrows являются двумя уникальными keyboard-layout; gamepad назначается descriptor с runtime index/profile. Для ответа используются физические позиции north/east/south/west, для обычных тем — прямые позиции west/north/east, для бонуса — D-pad up/down/right/left. Keyboard repeat игнорируется, gamepad polling сравнивает предыдущий snapshot. Новый экран disarmed до нейтрального состояния всех релевантных кнопок.

Скрытый selector до reveal отдаёт только `hasAnswered`; выбранная позиция остаётся внутри домена. Командные ромбы и device glyphs — разные CSS-компоненты и системы формы.

### 7. Browser adapters изолируют storage, clocks и Web Audio

`localStorage` содержит versioned envelope для одного snapshot, отдельной compact history и preferences. Декодеры fail-safe игнорируют неизвестную версию/повреждение. Snapshot с несовместимым `catalogRevision` не продолжается молча. Значимые переходы сохраняются синхронно; восстановленная партия всегда paused.

Audio adapter синтезирует короткие невербальные сигналы Web Audio после пользовательского жеста, без сетевых файлов. Ошибка/недоступность audio не влияет на reducer.

### 8. React рендерит projection, а не внутреннее состояние

Application controller связывает reducer, scheduler effects, persistence и adapters. React получает `GameViewModel` для текущей фазы и dispatch-функции. Экранная композиция остаётся DOM/CSS, использует локальный Onest, CSS custom properties команд/контраста/размера текста и отключаемые event-анимации.

Для browser QA добавляются data-testid только на ключевые семантические поверхности, не на визуальную структуру.

### 9. Проверка разделена по слоям

- Unit: reducer, clocks, fairness, scoring, tie-break, invalid commands, pause, selectors, PRNG/bags, storage codecs, input edges.
- Content: все 900 записей и review manifest.
- Browser: меню, 2–4 keyboard-controlled teams, normal/bonus flow, таймер через управляемый clock, reveal, standings, pause/restart/restore, accessibility и 1280/1920 overflow.
- Manual: фактические Xbox/PlayStation/Nintendo/unknown gamepads и полная групповая партия. Синтетический Gamepad API не считается доказательством физического сценария.

## Risks / Trade-offs

- [900 вопросов создают фактологический и редакторский риск] → независимые тематические файлы, обязательные source/date, schema-check и перекрёстное агентское ревью до интеграции.
- [Browser не даёт стабильную постоянную идентичность gamepad] → snapshot хранит descriptor, но после disconnect/restart требует явного нового нажатия для назначения.
- [Большой текст может переполнить 720p] → лимиты контента, responsive typography, отдельные 1280/1920 browser assertions и крупный режим с измерением overflow.
- [localStorage может быть повреждён или исчерпан] → versioned codecs, fail-safe fallback и ненавязчивое предупреждение; текущая партия продолжает работать в памяти.
- [Реальная доступность gamepad зависит от оборудования] → keyboard flow завершается автоматически, физические профили остаются явно непроверенными до ручного gate.
- [Sudden-death теоретически может исчерпать конечный hard-каталог] → после полного исчерпания разрешён новый seeded-цикл hard-вопросов с защитой порядка и границы; повторы до исчерпания запрещены.

## Migration Plan

1. Сохранить foundation entrypoints и заменить только shell-композицию после готовности домена/каталога.
2. Добавить version `1` storage envelope; старых production-сохранений нет, повреждённые данные безопасно игнорируются.
3. Интегрировать content packages только после schema-check и cross-review.
4. Перед архивом выполнить full check, strict OpenSpec, production Chromium playtest, актуальные скриншоты и отдельный verify.

Rollback — возврат единственного change-коммита; новых внешних данных или серверных миграций нет.
