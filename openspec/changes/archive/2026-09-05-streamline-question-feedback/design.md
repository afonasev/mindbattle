## Context

См. мотивацию в `proposal.md` и поведенческий контракт в delta-specs. Текущий `difficulty-feedback` хранит по одному ответу на каждую команду и посылает v2-массив; это пересекает UI, domain state, сериализацию, ввод, контроллер, local API и content-audit. Рабочее дерево содержит несвязанный незавершённый change `add-solo-endless-mode`; его файлы и решения не входят в этот change.

## Goals / Non-Goals

**Goals:**

- Один сериализуемый общий результат фидбэка для каждого показанного вопроса: выбор жалобы, причины, заметка, курсор и устойчивый eventId.
- Детеминированная обработка любого назначенного ввода без командной идентичности и без completion barrier команд.
- Один v3 NDJSON-событие на результат, включая явный сигнал отсутствия претензий, с безопасным повтором после ошибки.
- Сохранение v1/v2-журнала для чтения и отдельного отображения в сводках.

**Non-Goals:**

- Не изменять очки, время, seed, порядок вопросов, tie-break, состав команд или настройки назначения устройств.
- Не строить автоматическую модерацию, классификацию, поиск или внешнюю отправку свободных заметок.
- Не мигрировать исторические v1/v2-события в v3 и не приписывать им отсутствие жалобы.

## Decisions

### Единое авторитетное состояние вместо командных ответов

`difficulty-feedback` остаётся фазой матчевого ядра, но содержит единственный результат: `hasComplaint` в начальном неопределённом состоянии, множество причин, необязательную заметку, позицию общего курсора и eventId. У фазы нет `responses`, teamId, скрытых выборов или завершений команд.

Первый экран имеет курсор на «Нет», но запись создаётся только отдельной командой подтверждения. Подтверждение «Нет» сразу запускает сохранение положительного сигнала и не открывает повторно ни выбор «Да/Нет», ни причины: при успехе применяется continuation, а при ошибке остаётся только минимальный экран повтора уже готового результата. При «Да» переход к причинам разрешён только после явного подтверждения; «Готово» требует хотя бы одну причину или непустую заметку. Выбор противоположной сложности удаляет другой флаг в том же reducer-переходе. Это сохраняет правила, снимок и replay воспроизводимыми.

Альтернатива — хранить инициировавший teamId, чтобы блокировать остальных, — отклонена: она возвращает командную принадлежность и не нужна для единого согласованного результата.

### Порядок общих действий и neutral gate

Адаптер всё ещё распознаёт физический источник для проверки его назначения, но отправляет feedback-команду без teamId. Reducer обрабатывает команды input frame слева направо и после изменения шага или завершения результата прекращает обработку остальных feedback-команд этого frame. Поэтому одновременные действия не создают несколько результатов и имеют стабильный исход, заданный порядком frame. Существующий neutral gate и rising-edge фильтрация применяются при открытии экрана и между его шагами.

Альтернатива — принимать несколько действий и выбирать победителя по команде — отклонена: это создаёт скрытое правило приоритета участников и усложняет целевой общий поток.

### Текст вводится UI, а не игровым ядром

Заметка — обычное локальное DOM-текстовое поле, доступное только после выбора пути жалобы. Непустая заметка сама образует валидный редакторский сигнал, даже если теги не выбраны. UI передаёт валидированную строку в единственную доменную команду обновления заметки; ядро хранит строку, ограниченную 500 Unicode-кодпоинтами, но не зависит от DOM, клавиатуры или браузера. Пока поле имеет фокус, UI не передаёт игровые клавиши в input router; после выхода возвращается общий навигационный ввод. Геймпад может открыть/закрыть поле, но не обязан вводить произвольный текст.

Альтернатива — свободный текст в canvas либо набор D-pad — отклонена: он ухудшает доступность и не соответствует обычному браузерному полю ввода.

### Изолированный v3 контракт и локальная безопасность

`DifficultyFeedbackEvent` получает v3-вариант: общие метаданные, `hasComplaint`, `complaintReasons` и опциональный `complaintNote`. Валидатор проверяет связность полей, уникальность, конфликт `too-easy`/`too-hard` и предел заметки до записи. NDJSON использует стандартное JSON-кодирование, поэтому новая строка в заметке не нарушает границы файла. Сводка считает показы и жалобы, но никогда не включает raw text в числовые агрегаты; заметки можно читать только из локальных v3-записей при ручном анализе.

События v1/v2 продолжают проходить валидацию и храниться как исторические отдельные форматы. Вновь созданные eventId используют новый префикс v3, что исключает конфликт с v1/v2 при повторе клиента.

### Снимки и обновление версии

Схема снимка матча повышается с v2 до v3. v3 фаза в ожидании записи восстанавливает тот же общий результат и eventId. Снимок v1/v2 вне фазы фидбэка мигрирует как сейчас; снимок v1/v2 внутри старой фазы фидбэка переводится непосредственно в уже сохранённый continuation без сетевого запроса. Это предотвращает отправку нового v3 или дубль старого события в середине обновления. Валидация старого NDJSON не зависит от миграции снимков.

## Risks / Trade-offs

- [Свободный текст может содержать личные или чувствительные сведения] → заметка остаётся только на loopback-машине, UI не добавляет идентификатор команды, а документация и интерфейс называют её локальной редакторской заметкой.
- [Общее действие двух источников в одном frame] → фиксированный порядок команд frame и ранняя остановка reducer-а, покрытые unit-тестом.
- [Старый снимок теряет незавершённую анкету] → он безопасно продолжает игру без новой отправки; историческая запись, если уже была подтверждена, остаётся в журнале.
- [Новая агрегированная сводка может ошибочно трактоваться как рейтинг качества] → в отчёте сохраняется количество показов и запрет автоматического изменения каталога.

## Migration Plan

1. Добавить v3 domain/event schema, валидаторы и миграцию snapshot schema v2 → v3.
2. Перевести reducer, контроллер и input adapter на общий результат; удалить только код, тесты и UI независимых анкет, не затрагивая игровую механику.
3. Научить сервер и audit-инструменты принимать/читать v3 вместе с v1/v2 и публиковать разделённые агрегаты.
4. Обновить `docs/GAME_SPEC.md`, выполнить строгую проверку и muted browser playtest.
5. Rollback до коммита возвращает приложение к v2; уже добавленные v3 NDJSON-строки не должны редактироваться и будут проигнорированы старой версией, поэтому откат допустим только до новой записи либо с сохранением файла для последующего возврата на v3.
