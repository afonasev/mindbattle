## MODIFIED Requirements

### Requirement: После каждого вопроса собирается независимый фидбэк команд
Система SHALL при включённом в конфигурации партии флаге `collectQuestionFeedback` после раскрытия и объяснения каждого обычного, бонусного и tie-break-вопроса открыть фидбэк для всех активных команд одновременно. Каждая команда MUST одним позиционным нажатием выбрать воспринимаемую сложность `trivial / easy / medium / hard`; до завершения этого шага всеми командами UI показывает только факт выбора, но не значение. Затем каждая команда MUST выбрать отношение к похожим вопросам `like / abstain / dislike` и может отметить ноль или несколько диагностических флагов: `unfamiliar-topic`, `unclear-wording`, `suspected-error`, `ambiguous-answer`, `too-niche-or-uninteresting`, `weak-answer-options`; эти отметки показываются публично с маркерами выбравших их команд. Фидбэк MUST не менять очки, время, состав претендентов, текущую сложность вопроса, shuffle-bag или содержание последующих партий.

#### Scenario: Сбор отключён в настройках партии
- **WHEN** `collectQuestionFeedback` выключен до старта партии и после раскрытия команда создаёт новое допустимое нажатие
- **THEN** система не создаёт анкету и событие фидбэка, не обращается к API и сразу применяет обычный continuation раскрытия

#### Scenario: Команды завершают анкеты одновременно
- **WHEN** несколько активных команд выбирают или подтверждают разные пункты на фидбэк-экране в одном input frame
- **THEN** система фиксирует изменения каждой команды независимо и результат не зависит от порядка команд в frame

#### Scenario: Флаг незнакомости с темой
- **WHEN** команда отмечает `unfamiliar-topic`
- **THEN** система сохраняет его только как контекст воспринятой сложности, а не как игровой ответ, ошибку вопроса или основание исключить голос из отчёта

#### Scenario: Команда завершила фидбэк
- **WHEN** команда явно подтверждает заполненную обязательную часть анкеты
- **THEN** её ответы блокируются до записи события, а остальным активным командам остаётся доступна их собственная анкета

#### Scenario: Не завершён фидбэк
- **WHEN** хотя бы одна активная команда ещё не завершила обязательную часть анкеты
- **THEN** система не переходит к следующему игровому экрану и не запускает игровые часы

### Requirement: Событие фидбэка минимально, анонимно и идемпотентно
Клиент SHALL отправлять одно версионированное событие v2 с уникальным eventId, непрозрачным matchId, catalogRevision, questionId, назначенной каталогом difficulty и массивом анонимных ответов завершивших фидбэк активных команд. Каждый ответ MUST содержать только perceivedDifficulty, similarityPreference и уникальный набор diagnosticFlags. Событие MUST не содержать имена, идентификатор команды, игровые ответы, счёт, демографические признаки, свободный текст или данные устройства.

#### Scenario: Первая запись события
- **WHEN** API получает валидный ранее не встречавшийся eventId
- **THEN** сервер один раз записывает событие, добавляет серверное время и подтверждает создание

#### Scenario: Повтор того же события
- **WHEN** API повторно получает тот же eventId с тем же содержимым
- **THEN** сервер не добавляет вторую строку и возвращает успешное идемпотентное подтверждение

#### Scenario: Конфликт eventId
- **WHEN** ранее записанный eventId приходит с другим содержимым
- **THEN** сервер отклоняет запрос как конфликт и не изменяет файл

#### Scenario: Невалидное событие
- **WHEN** отсутствует обязательное поле, массив ответов пуст, значение перечисления недопустимо, флаги повторяются либо questionId не существует в текущем каталоге
- **THEN** сервер отклоняет запрос с диагностикой и не изменяет файл

### Requirement: Сервер хранит append-only NDJSON-журнал
Локальный сервер SHALL последовательно дописывать каждое подтверждённое v2-событие отдельной UTF-8 JSON-строкой в файл по конфигурируемому пути и MUST обеспечивать валидные границы строк при конкурентных запросах. Родительский каталог SHALL создаваться при запуске, а существующие валидные события v1 и v2 SHALL сохраняться между перезапусками.

#### Scenario: Конкурентные разные события
- **WHEN** почти одновременно поступают несколько валидных событий с разными eventId
- **THEN** каждое событие присутствует в журнале ровно один раз как отдельная разбираемая JSON-строка

#### Scenario: Ошибка записи
- **WHEN** файл нельзя открыть, создать или дописать
- **THEN** сервер не подтверждает событие, клиент сохраняет завершённые анкеты и предлагает повторить отправку

#### Scenario: Восстановление ожидающей оценки
- **WHEN** приложение перезапущено со снимком партии, ожидающим подтверждения события
- **THEN** оно восстанавливает ответы всех команд, тот же eventId и может безопасно повторить отправку

### Requirement: Сервер предоставляет агрегированную сводку фидбэка
Система SHALL предоставлять read-only сводку по каждому questionId и назначенной difficulty: число анонимных ответов, количества каждого perceivedDifficulty и similarityPreference, количества диагностических флагов и те же агрегаты для ответов с `unfamiliar-topic`. Отчёт MUST показывать v1-сложность отдельно от v2 и не MUST автоматически переклассифицировать каталог. Повреждённые строки журнала MUST не включаться в агрегаты и SHALL быть отражены счётчиком диагностических ошибок.

#### Scenario: Сравнение сложности с контекстом темы
- **WHEN** запрошена сводка после нескольких игр с отметками `unfamiliar-topic`
- **THEN** ответ позволяет сравнить все воспринятые сложности с отдельным срезом незнакомой темы, не скрывая и не отбрасывая эти ответы

#### Scenario: Сигналы качества вопроса
- **WHEN** игроки отметили diagnosticFlags или `dislike`
- **THEN** сводка показывает количества каждого сигнала по questionId без связи с конкретной командой или игровым ответом

#### Scenario: Пустой журнал
- **WHEN** ещё не сохранено ни одного события
- **THEN** сервер возвращает нулевые агрегаты и нулевой счётчик повреждённых строк
