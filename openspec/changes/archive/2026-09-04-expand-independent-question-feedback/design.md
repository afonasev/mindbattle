## Context

См. [proposal.md](proposal.md). Сейчас serializable `difficulty-feedback` хранит одну nullable difficulty и event v1; первый допустимый ввод прекращает обработку остальных команд. Локальный API и NDJSON-журнал принимают только v1, а сводка строит exact/lower/higher. Все команды находятся перед одним экраном, однако после tie-break часть из них становится зрителями; фидбэк собирается только с активных команд, как определяет доменное состояние.

## Goals / Non-Goals

**Goals:**

- Собрать один независимый ответ каждой активной команды атомарно для одного раскрытого вопроса.
- Сохранить независимость выбора при нескольких командах в одном input frame и при перезапуске до server ack.
- Сохранить анонимность persisted event и читаемость журнала v1.
- Дать редактору стратифицированный, но не автоматически интерпретируемый сигнал о знакомости с темой.

**Non-Goals:**

- Не собирать correctness-rate, игровые ответы, teamId, демографию, свободный текст или историю команды.
- Не менять игровую сложность каталога, scoring, часы, random seed, reveal, tie-break и статус зрителя.
- Не добавлять сетевую синхронизацию, внешние сервисы или production analytics.

## Decisions

### 1. Авторитетное состояние хранит ответы по teamId только до отправки

`DifficultyFeedbackPhase` v2 хранит serializable map по active `teamId`, где у каждой команды есть текущий шаг, выборы и `completed`. Это необходимо ядру исключительно для валидации права команды на ввод, одновременной обработки и восстановления снимка. Domain commands выражают изменение текущей анкеты либо её завершение; они не затрагивают таймеры и не допускают изменение `completed`-ответа.

Когда все active teams завершены, application layer строит event v2. Он удаляет ключи `teamId`, сериализует только значения ответов в детерминированном каноническом порядке значений и сохраняет ровно один `feedback-v2:<match>:<round>:<question>` eventId. Порядок элементов не является идентификатором команды; server и summary не восстанавливают соответствие с командой.

Альтернатива — отдельный POST на команду — отвергнута: она усложняет частичную запись, retry и может сохранить связь eventId с teamId. Альтернатива — хранить только aggregate в domain — отвергнута: нельзя проверить право каждой команды закончить фидбэк и восстановить незавершённый экран.

### 2. Скрытая сложность и публичная доска тегов используют directional control

На `difficulty` один positional press немедленно выбирает значение (`west / north / east / south` = `trivial / easy / medium / hard`). UI до completion barrier показывает только «выбирает» либо «сложность выбрана» и не отображает значение. После barrier все команды параллельно управляют собственным курсором на публичной доске стрелками/D-pad, а отдельная кнопка подтверждения переключает текущий необязательный флаг, выбирает реакцию `like / abstain / dislike` или завершает анкету. Доска показывает маркеры команд у реакции и флагов; `unfamiliar-topic` — такой же toggle-флаг. `Space` подтверждает для WASD, правый `Shift` — для стрелок, нижняя face-кнопка — для геймпада.

Adapter создаёт neutral gate после каждого positional press сложности и после изменения интерактивного шага: одно удержание не может перейти на доску тегов или завершить анкету. Одинаковые команды разных teamId из одного frame редьюсер применяет целиком; команда, уже completed, игнорируется. Это обеспечивает отсутствие first-input-wins зависимости.

Альтернатива — одновременно разместить все controls на одной карточке — отвергнута: она не оставляет однозначного mapping для пяти+ позиций на четырёх направляющих input и хуже читается на общем экране.

### 3. Сервер принимает v1 и v2, но выдаёт раздельные агрегаты

Валидация local API распознаёт `schemaVersion: 1` и прежний payload, а также v2. Новый payload содержит нужные metadata и непустой массив ответов с допустимыми enum и уникальными flags; число ответов и заполненность каждой активной анкеты проверяются domain/application до POST, поскольку сервер не имеет и не получает team roster. Server по-прежнему валидирует questionId и assignedDifficulty по каталогу и выполняет idempotency по полному payload.

Summary не смешивает v1 консенсус с v2 независимыми ответами: показывает отдельные счётчики и в v2 — total, per-difficulty, similarity, flags, плюс срез `unfamiliar-topic`. Ни v1, ни v2 не дают автоматически менять difficulty; отчёт отображает контекст как отдельное измерение, а не фильтр.

Альтернатива — мигрировать существующие строки v1 в несколько синтетических ответов — отвергнута: она выдумывает несуществующие голоса. Альтернатива — отказаться от v1-строк — отвергнута, потому что это теряет уже собранный редакторский сигнал.

### 4. Снимки мигрируются без потери retry

Новые snapshots получают schema v2. Старый snapshot вне feedback phase мигрируется структурно. Старый snapshot, уже находящийся в v1 feedback phase с выбранной общей оценкой, сохраняет legacy-вариант и при retry отправляет исходный v1 event; его нельзя корректно разложить на независимые ответы. После его continuation все новые вопросы используют v2. Неизвестный или повреждённый v2 snapshot отклоняется по существующей безопасной стратегии восстановления.

### 5. Границы ответственности и честности

Domain владеет roster active teams, фазой, командами анкеты, completion barrier и continuation. Input adapter переводит физический input в team-scoped feedback commands и neutral gates. React/CSS показывают карточки и не вычисляют право команды завершить анкету. Application/controller создаёт v2 payload, управляет pending/error/retry. Client/server adapter валидирует, хранит и агрегирует append-only events. Renderer, audio и clocks не участвуют.

Случайность не используется. Одновременные команды применяются детерминированно по `teamId`, но независимые изменения разных команд коммутативны; при двух conflicting commands одной команды в frame действует их source sequence. Потеря фокуса или контроллера сохраняет действующую pause policy: фидбэк не продвигается до resume и не отправляется частично. Минимально поддерживается конфигурация из двух активных команд; при tie-break только contenders являются active и дают фидбэк, остальные остаются зрителями.

### 6. Сбор обратной связи — настройка партии

`MatchConfig.collectQuestionFeedback` — сериализуемый флаг новой партии, по умолчанию `true`. Он показывается до старта в настройках партии, а restart повторяет исходное значение. Для старых или вручную созданных конфигураций отсутствие поля интерпретируется как `true`; созданная или восстановленная новая партия хранит явное значение, поэтому восстановление снимка не меняет выбор ведущего.

Когда флаг `false`, новое нажатие после раскрытия проходит существующий neutral gate, но сразу применяет continuation раскрытия: следующая тема, таблица результатов, очередной финальный выбор тем или победитель. Domain не создаёт `difficulty-feedback` phase, application не формирует и не отправляет event, server и NDJSON-журнал не получают запись. Этот обход не затрагивает счёт, часы, seed, history, состав претендентов и порядок выбора темы.

## Risks / Trade-offs

- [Дополнительные шаги затягивают партию] → короткие directional controls, необязательные flags и явный status готовности вместо отдельных экранов.
- [Общий экран не может обеспечить физическую тайну выбора] → UI не показывает ответы соперникам; спецификация не обещает регулировать разговоры или взгляд на общий экран.
- [Незнакомость с темой может стать оправданием неправильного ответа] → не связывать её с correctness и не исключать такие голоса из отчёта.
- [V1 и v2 усложняют summary] → строгий discriminated schema, отдельные агрегаты и тесты повреждённых/смешанных строк.
- [Изменение снимка прерывает retry] → legacy phase и сохранение eventId/payload при миграции, unit-тест восстановления.

## Migration Plan

1. Ввести discriminated v1/v2 feedback schema, snapshot v2 и обратное чтение v1.
2. Изменить domain phase, команды и selectors, сохранив legacy continuation для незавершённого v1 snapshot.
3. Заменить input/UI на параллельные карточки и per-source neutral gates.
4. Обновить controller, local API, NDJSON parser и summary; существующий журнал не переписывать.
5. Пройти deterministic domain/API tests, browser QA в 1280×720 и 1920×1080 с выключенным звуком и реальный локальный плейтест минимум двух команд с разными keyboard/gamepad схемами; browser/hotfix flow выключает сбор фидбэка явно, кроме тестов этой механики.
6. Перед коммитом выполнить strict OpenSpec validation, проектные проверки и проверку точного staged scope. Rollback — Git revert change-коммита; v1 журнал и snapshots не удаляются.
