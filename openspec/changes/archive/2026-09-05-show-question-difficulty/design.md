## Context

См. мотивацию в `proposal.md`. Вопросная фаза уже содержит назначенную сложность в сериализуемом `round`, а оба UI-потока получают тот же снимок вопроса при открытии фидбэка. `docs/GAME_SPEC.md` требует DOM/CSS-представление без зависимости авторитетного ядра от UI.

## Goals / Non-Goals

**Goals:**

- Создать единый formatter отображения `easy`/`medium`/`hard` как «Лёгкий»/«Средний»/«Сложный».
- Подать маркировку из текущего вопроса в шапки командного и соло-потоков, а также в соответствующие фидбэк-состояния.
- Проверить текстовое представление автоматизированными UI-тестами и визуально в muted Chromium.

**Non-Goals:**

- Не менять `Difficulty`, каталог, события фидбэка, state machine, seed, очки, таймеры или порядок вопросных слотов.
- Не добавлять уровню новый цвет, иконку, доступность-настройку или видимость на других экранах.

## Decisions

### Один presentation formatter

Обе UI-поверхности используют один локальный formatter для трёх существующих значений сложности. Это исключает расхождение словоформ между шапкой и фидбэком и не добавляет данных в доменную модель. Альтернатива — повторить switch в каждом компоненте — отвергнута: при одинаковом публичном термине она повышает риск расхождения.

### Сложность читается только из текущего round

Командный и соло UI получают назначенную сложность из уже отображаемого вопроса/round, включая сохранённую фазу фидбэка. Новый UI state, persistence или API-поле не вводятся. Альтернатива — сохранять отдельную UI-копию — отвергнута: она может расходиться с сериализуемым состоянием и не даёт нового поведения.

### Маркировка остаётся текстовой частью заголовка

В вопросной шапке значение присоединяется в круглых скобках после счётчика, а фидбэк показывает явную текстовую подпись уровня. Существующие стили заголовков и accessibility-режимы сохраняют читаемость; выбранное значение не передаётся только цветом. Альтернатива — самостоятельный декоративный badge — отвергнута, потому что пользователь утвердил скобочный формат, а badge добавил бы новую визуальную конкуренцию с вопросом.

## Risks / Trade-offs

- [Командный и соло UI используют разные компоненты] → вынести formatter в общий presentation-модуль и покрыть оба пути тестами.
- [Скобочная подпись может не поместиться при крупном тексте] → проверить 1280×720 и крупный текст в браузере; при необходимости разрешить безопасный перенос без усечения.
- [Фидбэк может восстановиться из snapshot] → тестировать отображение для обычного открытия и retry, не меняя eventId или полезную нагрузку.

## Migration Plan

1. Добавить formatter и подключить его к четырём UI-точкам.
2. Дополнить UI-тесты для easy/medium/hard, командного, соло и фидбэк-состояний.
3. Выполнить typecheck, unit-тесты и muted browser-проверку с тремя скриншотами.
4. При откате удалить только presentation formatter, разметку, стили и тесты; сохранённые партии и локальный фидбэк остаются совместимыми.
