## MODIFIED Requirements

### Requirement: После каждого вопроса собирается единый фидбэк о претензии
Система SHALL при включённом в конфигурации партии флаге `collectQuestionFeedback` после раскрытия и объяснения каждого обычного, бонусного и tie-break-вопроса открыть один общий экран «Хотите пожаловаться на вопрос?». Пункт «Нет» MUST быть выделен по умолчанию, но не отправлен до явного подтверждения после neutral gate. Результат не имеет принадлежности команде: любое новое допустимое действие любого назначенного источника MUST менять один общий выбор. При «Да» система MUST показать причины `too-easy`, `too-hard`, `weak-answer-options`, `unclear-wording`, `suspected-error`, `ambiguous-answer` и `uninteresting-for-quiz`; требуется выбрать хотя бы одну, допускается несколько, а `too-easy` и `too-hard` MUST быть взаимоисключающими. К жалобе разрешена одна необязательная текстовая заметка не длиннее 500 символов. Фидбэк MUST не менять очки, время, состав претендентов, текущую сложность вопроса, shuffle-bag или содержание последующих партий.

#### Scenario: Сбор отключён в настройках партии
- **WHEN** `collectQuestionFeedback` выключен до старта партии и после раскрытия команда создаёт новое допустимое нажатие
- **THEN** система не создаёт экран и событие фидбэка, не обращается к API и сразу применяет обычный continuation раскрытия

#### Scenario: Нет претензий
- **WHEN** после neutral gate любой назначенный источник подтверждает выделенный по умолчанию пункт «Нет»
- **THEN** система фиксирует единый результат без жалобы, не открывает повторно выбор «Да/Нет», список причин или текстовую заметку, а после подтверждённой записи сразу применяет continuation

#### Scenario: Жалоба с несколькими причинами
- **WHEN** на общем экране подтверждено «Да» и выбраны `weak-answer-options` и `uninteresting-for-quiz`
- **THEN** система сохраняет обе причины в одном общем результате без маркера или идентификатора команды

#### Scenario: Противоположные оценки сложности
- **WHEN** в результате жалобы выбрана `too-easy`, а затем подтверждается `too-hard`
- **THEN** `too-easy` снимается, а в результате остаётся только `too-hard`

#### Scenario: Пустая жалоба
- **WHEN** игроки пытаются завершить путь «Да», не выбрав ни одной причины
- **THEN** система не отправляет событие и явно сообщает, что нужно выбрать минимум одну причину

#### Scenario: Свободная заметка
- **WHEN** игроки добавляют к валидной жалобе текст до 500 символов
- **THEN** текст сохраняется только в том же локальном событии, не связывается с командой или игровым ответом и не изменяет выбранные причины

### Requirement: Событие фидбэка минимально, анонимно и идемпотентно
Клиент SHALL отправлять одно версионированное событие v3 с уникальным eventId, непрозрачным matchId, catalogRevision, questionId, назначенной каталогом difficulty, булевым `hasComplaint`, уникальным массивом complaintReasons и необязательной complaintNote. При `hasComplaint: false` массив причин MUST быть пустым, заметка MUST отсутствовать; при `hasComplaint: true` массив MUST содержать хотя бы одну допустимую причину, не включать одновременно `too-easy` и `too-hard`, а заметка при наличии MUST иметь не более 500 символов. Событие MUST не содержать имена, идентификатор команды, игровые ответы, счёт, демографические признаки или данные устройства.

#### Scenario: Положительный сигнал
- **WHEN** API получает новое валидное v3-событие с `hasComplaint: false`
- **THEN** сервер один раз записывает событие как отсутствие претензий и подтверждает создание

#### Scenario: Первая запись события
- **WHEN** API получает валидное ранее не встречавшееся v3-событие с `hasComplaint: true`
- **THEN** сервер один раз записывает причины и необязательную заметку, добавляет серверное время и подтверждает создание

#### Scenario: Повтор того же события
- **WHEN** API повторно получает тот же eventId с тем же содержимым
- **THEN** сервер не добавляет вторую строку и возвращает успешное идемпотентное подтверждение

#### Scenario: Конфликт eventId
- **WHEN** ранее записанный eventId приходит с другим содержимым
- **THEN** сервер отклоняет запрос как конфликт и не изменяет файл

#### Scenario: Невалидное событие
- **WHEN** отсутствует обязательное поле, причины не согласованы с `hasComplaint`, причина повторяется, одновременно выбраны противоположные сложности, заметка длиннее 500 символов либо questionId не существует в текущем каталоге
- **THEN** сервер отклоняет запрос с диагностикой и не изменяет файл

### Requirement: Сервер хранит append-only NDJSON-журнал
Локальный сервер SHALL последовательно дописывать каждое подтверждённое v3-событие отдельной UTF-8 JSON-строкой в файл по конфигурируемому пути и MUST обеспечивать валидные границы строк при конкурентных запросах. Родительский каталог SHALL создаваться при запуске, а существующие валидные события v1 и v2 MUST сохраняться и оставаться отдельно читаемыми между перезапусками.

#### Scenario: Конкурентные разные события
- **WHEN** почти одновременно поступают несколько валидных событий с разными eventId
- **THEN** каждое событие присутствует в журнале ровно один раз как отдельная разбираемая JSON-строка

#### Scenario: Ошибка записи
- **WHEN** файл нельзя открыть, создать или дописать
- **THEN** сервер не подтверждает событие, клиент сохраняет общий выбранный результат и предлагает повторить отправку

#### Scenario: Восстановление ожидающей оценки
- **WHEN** приложение перезапущено со снимком партии, ожидающим подтверждения события
- **THEN** оно восстанавливает общий результат, тот же eventId и может безопасно повторить отправку

### Requirement: Сервер предоставляет агрегированную сводку фидбэка
Система SHALL предоставлять read-only сводку v3 по каждому questionId и назначенной difficulty: число показов, количество жалоб, количество отсутствия жалоб и количества каждой причины. Сводка MUST показывать v1, v2 и v3 отдельно, не MUST автоматически переклассифицировать каталог и MUST исключать текст заметок из числовых агрегатов. Повреждённые строки журнала MUST не включаться в агрегаты и SHALL быть отражены счётчиком диагностических ошибок.

#### Scenario: Сравнение сложности с контекстом темы
- **WHEN** для вопроса записаны девять результатов без жалобы и одна жалоба `too-hard`
- **THEN** сводка показывает десять показов, одну жалобу, девять отсутствий жалобы и одну отметку `too-hard`

#### Scenario: Сигналы качества вопроса
- **WHEN** редактор читает локальный NDJSON-журнал для разбора жалоб
- **THEN** он может увидеть заметку только в полной v3-записи без связи с командой, игроком или игровым ответом

#### Scenario: Пустой журнал
- **WHEN** ещё не сохранено ни одного события
- **THEN** сервер возвращает нулевые агрегаты и нулевой счётчик повреждённых строк
