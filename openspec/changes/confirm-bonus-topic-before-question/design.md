## Context

См. `proposal.md` — Why и delta-specs. Сейчас последний отдельный бонусный запрет внутри авторитетного reducer сразу вызывает выбор вопроса и переводит матч из `bonus-veto` в `answering`. Для обычной темы уже существует сериализуемая фаза `topic-confirmation`, общий frame clock, пауза, восстановление, проекция, DOM-экран и input mode `continue` с neutral gate.

Бонусность текущего основного вопроса уже однозначно выводится из `config` и `mainQuestionIndex`; она влияет на очки независимо от вида фазы. Внешних сервисов, сетевой синхронизации и новых зависимостей change не требует.

## Goals / Non-Goals

**Goals:**

- Переиспользовать одну авторитетную фазу подготовки для обычной и бонусной темы без дублирования clock/input/pause-логики.
- Отложить выбор конкретного вопроса, расход seeded random и отметку вопроса использованным до фактического начала ответа.
- Сохранить совместимость существующих snapshot schemaVersion 1 и старых снимков `topic-confirmation`.
- Сделать бонусный вариант визуально отличимым внутри существующей композиции подтверждения.

**Non-Goals:**

- Менять bonus-veto, множитель, длительность подготовки, правила раннего пропуска или tie-break.
- Добавлять новые кнопки, pointer/touch-действия, анимацию, звук либо отдельный UI layout.
- Доказывать физический многопользовательский сценарий виртуальным gamepad-вводом.

## Decisions

### 1. Завершённый bonus-veto создаёт существующую фазу `topic-confirmation`

После вычисления единственной незапрещённой темы reducer фиксирует её в `selectedTopicIds`, но вместо немедленного вызова выбора вопроса записывает `topic-confirmation` с тем же `topicId` и `remainingMs: 3000`, что обычный выбор. Автоматическое окончание clock и семантическая команда `continue` продолжают использовать общий путь запуска main-вопроса.

Так вопрос не выбирается и seeded random не расходуется, пока он не становится видимым. Альтернатива — заранее создать `RoundState` и скрыть его за UI — отклонена из-за преждевременной записи вопроса в историю и более сложного snapshot.

### 2. Бонусность не добавляется в сериализованную фазу

Проекция определяет вариант экрана через существующие `config` и `mainQuestionIndex` и передаёт UI вычисленный признак бонуса. `TopicConfirmationPhase` и строгий snapshot validator остаются без изменений, поэтому старые снимки продолжают читаться, а восстановленный бонусный экран получает корректную маркировку детерминированно.

Альтернатива с новым полем `kind: normal | bonus` отклонена: она дублирует выводимое правило и требует миграции либо ослабления валидатора.

### 3. Neutral gate и порядок команд остаются общими

Переход `bonus-veto → topic-confirmation` меняет phase kind, поэтому клиент разоружает физический ввод до полного neutral. Reducer после команды, изменившей фазу, прекращает обработку остальных команд текущего frame; удержанный финальный запрет не становится `continue` или ответом. Только новое действие активной команды может запустить вопрос раньше.

Альтернатива с отдельной командой подтверждения бонуса отклонена: она создала бы лишнюю ветку физического ввода и отличалась бы от уже утверждённого обычного экрана.

### 4. UI переиспользует существующую композицию подтверждения

Один DOM-компонент сохраняет название темы, счётчик и control hint. Для бонусного варианта меняется stage label на «Бонусный вопрос · x2» и текст о начале бонусного вопроса; действующие CSS, responsive layout и reduced-motion поведение сохраняются.

### 5. Проверка разделяет правила и браузерный результат

Доменный тест фиксирует промежуточную фазу, отсутствие начатого вопроса, полный базовый таймер после авто- и ручного перехода, паузу и сериализацию. Browser-тест доходит до первого бонусного выбора, завершает запреты, проверяет neutral gate и снимает актуальный screenshot подтверждения при выключенном звуке. DOM, console и screenshot собираются на одном origin и одном dev-сервере.

## Risks / Trade-offs

- [Переход bonus-veto изменит вспомогательные тестовые циклы, ожидающие немедленный вопрос] → обновить единый helper выбора текущей темы и добавить отдельные assertions промежуточной фазы.
- [Бонусный экран потеряет x2 при restore] → вычислять признак только из сериализуемых `config` и `mainQuestionIndex`, покрыть восстановление тестом.
- [Финальный запрет случайно пропустит экран] → сохранить phase-change early return reducer и проверить удержание/neutral gate в browser-тесте.
- [Три секунды замедлят партию] → утверждённый ранний переход остаётся доступен любому активному назначенному источнику.

## Migration Plan

1. Изменить только переход после последнего бонусного запрета и вычисляемую публичную проекцию; формат snapshot не менять.
2. Адаптировать общий компонент подтверждения и тестовые helpers к промежуточной фазе.
3. Выполнить unit/build/browser-проверки, снять screenshot без звука и синхронизировать delta-specs с основными перед архивированием.
4. При откате вернуть прямой запуск вопроса после bonus-veto; сохранённые фазы останутся структурно валидными и безопасно продолжатся существующим путём.
